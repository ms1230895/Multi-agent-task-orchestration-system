# Spec: Evaluation

**Status:** Approved
**Branch:** feature/evaluation
**Date:** 2026-10-17

## 1. Goal
Measure the real numbers of the system: run the full benchmark passes (main model with the gate off and on, the second model on), find the top 3 failure causes from the traces, fix them as separate small changes, run fresh passes on the fixed code, and save a results table plus a short honest analysis in `docs/results.md`. Two read-only tools are built for this: `evaluation/report.py` (compares passes) and `evaluation/analyze.py` (reads the traces of a pass and groups its failures).

## 2. Why
Every CV number comes from this session: the task success rate, the failed-tool-call reduction from the gate (off vs on), and the count of traced runs. Session 6 built the measuring tool for **one** pass; nothing yet compares passes, and nothing turns 30 traces into a list of failure causes. Doing that by hand is slow and error-prone, and copying numbers into a doc by hand is how wrong numbers end up on a CV.

The numbers are only honest if:
- passes are compared only when they differ in exactly the one thing being measured (the gate flags, the model, or the code fix),
- results from before and after a fix are never pooled together (roadmap 7),
- the numbers in `docs/results.md` are generated by code from the committed results, not typed by hand,
- weak results are reported as they are, even below the targets (~65% success, ~20% reduction).

Architecture layer: a new read-only layer on top of layer 7 (Benchmark). It reads `benchmark/results/` and `logs/`; it never runs a task and never calls an LLM. The fixes themselves go into `src/` (layers 4 to 6), chosen after the baseline analysis (section 5.6).

## 3. Scope
**In scope:**
- `evaluation/__init__.py` (new, empty package marker).
- `evaluation/passes.py` (new): load a pass folder, per-pass metrics, the Wilson interval, grouping of identical passes.
- `evaluation/report.py` (new): comparisons (ablation, model, before/after fix), trace count, the Markdown results block, `--write` into `docs/results.md`, CLI.
- `evaluation/analyze.py` (new): per-pass trace analysis (outcome classes, failed tool calls, repeated failing calls, critic rejections without a tool call, iteration-limit hits, tool not used), a digest of every failed task, CLI.
- Real passes, run by Gaurav (section 5.5): baseline `main-off-1`, `main-on-1`, `second-on-1`; after the fixes `main-on-2`, `main-off-2`, `second-on-2`; `second-off-2` if quota allows.
- Up to 3 fixes in `src/`, one per top failure cause, each its own commit with a test and a decision entry. Which fixes is decided after the baseline analysis, in a spec addendum (section 5.6).
- `docs/results.md` (new): generated results block plus hand-written setup, failure analysis, fixes, and limitations.
- `docs/analysis/<pass_id>.md` (new): the saved `analyze` output for each analysed pass.
- Docs: `docs/specs/architecture.md` (section 2 layer table and section 5: the evaluation tools, pass naming, the comparison rules), `docs/plans/decisions.md`, CLAUDE.md (commands and layout), `docs/project-memory.md` (commands).
- Unit tests for `evaluation/`, fully mocked (scripted pass folders and traces in `tmp_path`).

**Out of scope:**
- Any change to `benchmark/tasks.json`, `benchmark/checkers.py`, `benchmark/text.py`, `benchmark/tasks.py`, or an expected answer (Hard rule 6). A task found to be badly worded is written down as a limitation, not edited.
- Any change to `benchmark/runner.py` in this session (it is in the code fingerprint; see section 5.1).
- Changing `.env` settings as a "fix". Fixes are code only; the config of each side stays the same before and after (section 5.4).
- An LLM judge or an LLM that labels failures. The analysis tool groups failures with code; a human (Gaurav and Claude) reads the digests and names the causes.
- Charts and the dashboard: session 8. This session produces Markdown tables only.
- Statistical tests beyond the Wilson interval (30 tasks is too few for more to mean much).
- Running passes in parallel.

```python
# evaluation/passes.py
class ReportError(Exception): ...    # a pass is missing, broken, or the id is invalid

@dataclass(frozen=True)
class PassData:
    pass_id: str

    results: list[dict[str, Any]]     # lines of results.jsonl
    pauses: int                       # lines of paused.jsonl

def pass_metrics(data: PassData) -> dict[str, Any]
def group_key(data: PassData) -> tuple[str, str, str, tuple[str, ...]]  # model, config JSON, fingerprint, task ids
def group_passes(passes: list[PassData]) -> list[PassGroup]            # complete passes only

@dataclass(frozen=True)
class PassGroup:
    pass_ids: list[str]               # in manifest started_at order
    model: str
    config: dict[str, Any]
    fingerprint: str
    task_ids: list[str]

    metrics: dict[str, Any]           # pooled: counts summed over the passes, rates recomputed

# evaluation/report.py

def compare_groups(groups: list[PassGroup]) -> tuple[list[Comparison], list[str]]   # rows, "not compared" reasons
def count_traces(logs_dir: Path = LOGS_DIR) -> int                   # run_end events in logs/*.jsonl
def render_markdown(passes: list[PassData], logs_dir: Path = LOGS_DIR) -> str
def write_block(doc_path: Path, block: str) -> None                  # raises ReportError
def main(argv: list[str] | None = None) -> int

# evaluation/analyze.py
OutcomeClass = Literal["success", "infra", "crash", "wrong_answer", "planner_failed",
                       "gave_up_right_answer", "gave_up", "other"]
def classify(result: dict[str, Any], trace: list[dict[str, Any]] | None) -> OutcomeClass
def error_kind(error: str) -> str
def analyze_pass(data: PassData, logs_dir: Path = LOGS_DIR) -> dict[str, Any]
def render_analysis(pass_id: str, analysis: dict[str, Any]) -> str   # Markdown
def main(argv: list[str] | None = None) -> int
```

## 5. Design

### 5.1 Why a new `evaluation/` folder, and nothing changed in `benchmark/`
The code fingerprint (D34) covers `src/**/*.py`, `benchmark/*.py` and `benchmark/tasks.json`. If the report tool lived in `benchmark/`, every edit to it would change the fingerprint: a baseline pass could not be resumed after a pause, and `main-off-1` and `main-on-1` might end up with different fingerprints although the agent code is the same. In `evaluation/`, the tools can be built and fixed **while** the baseline passes run, without touching any fingerprint. A test proves that an edit in `evaluation/` leaves the fingerprint unchanged (AC23).

For the same reason, `benchmark/runner.py` is not edited. `evaluation/passes.py` reuses the runner's public names (`summarize`, `is_infra_error`, `RESULTS_DIR`, `MANIFEST_NAME`, `RESULTS_NAME`, `PAUSED_NAME`, `PASS_ID_PATTERN`, `CATEGORY_ORDER`) and imports three private helpers by name: `_read_manifest`, `_read_results`, `_redact`. **Why import and not copy:** results are then read and redacted exactly as the runner writes them; a copy could drift. A `# WHY:` comment says this, and making them public is listed as deferred (open question 3). `PassRefused` from those helpers is turned into `ReportError`.

`src/logger.py` provides `read_trace(path)` and `trace_path(run_id)`, which `analyze.py` uses to read traces.

### 5.2 `evaluation/passes.py`: one pass and groups of passes
**`load_pass(pass_id)`**: checks the id with `PASS_ID_PATTERN` (otherwise `ReportError`), reads `manifest.json` (`_read_manifest`), `results.jsonl` (`_read_results`) and counts the non-empty lines of `paused.jsonl`. A missing folder, a broken manifest or a broken results line gives `ReportError` naming the pass (and the line number, from the runner's message).

**`pass_metrics(data)`**: calls the runner's `summarize(results, planned=..., infra_pauses=...)`, so the headline numbers use exactly the session 6 definitions (architecture 5), then adds:
- `success_ci`: `wilson_interval(successes, tasks_done)`;
- `validation_errors`, `tool_retries`, `step_retries`, `replans`: summed from the result counters (a missing or non-int counter counts as 0, like `summarize`);
- `runs_with_failed_call`: results whose `failed_tool_calls` counter is above 0;
- `median_duration_s`: median of `duration_ms` / 1000, `None` without results;
- `complete`, `model`, `enable_validation`, `enable_retry`, `fingerprint_short` (the first 8 hex characters after `sha256:`), `git_commit` (first 7), `git_dirty`.

These secondary numbers are defined now, before measuring, like the headline ones.

**`wilson_interval(k, n)`**: the 95% Wilson score interval for k successes out of n. `None` when n is 0. **Why:** with 30 tasks, one task is 3.3 percentage points; the interval shows how far apart two rates must be before the difference means something. Every success rate in the report is printed with it.

**Groups.** Passes with the same `group_key` (model, `config` as sorted JSON, `code_fingerprint`, `task_ids`) are repeats of the same experiment. `group_passes` puts complete passes into groups and pools them: counts summed (successes, results, tool calls, failed calls, ...), rates recomputed from the sums, never averaged. An incomplete pass is never in a group. **Why pooled sums:** a repeat pass (`main-on-3`) adds evidence; averaging rates of passes with different sizes would weight them wrongly. Passes with different fingerprints are never in the same group, so before-fix and after-fix results are never mixed.

### 5.3 `evaluation/report.py`: comparisons and the results block
**`compare_groups(groups)`** looks at every pair of groups with the same `task_ids` and makes a row when they differ in exactly one thing:

| Kind | Same | Differs | Row shows |
|---|---|---|---|
| `ablation` | model, fingerprint, every config key except the two flags | off group has `enable_validation` and `enable_retry` both `false`, on group both `true` | failed-tool-call rate off and on (with counts), absolute difference in percentage points, **relative reduction** = (off − on) / off, success rate off and on with intervals, validation errors, tool retries |
| `model` | fingerprint, every config key except `ollama_model` | `ollama_model` | success rate (with interval) and failed-tool-call rate of each model, by category |
| `fix` | model, every config key | fingerprint | before (earlier `started_at`) and after: success rate with interval, failed-tool-call rate, step retries, replans, outcome counts |

- Relative reduction is `None` (printed `n/a`) when the off rate is `None` or 0. A negative value is printed as an increase (`-12.5%, the gate added failed calls`), never hidden.
- Pairs that share `task_ids` and model but fit no kind give a "not compared" line naming why (for example `main-off-1 vs main-on-2: different code and different flags`). **Why:** a missing ablation row must never be silent; it usually means `.env` changed by mistake.

**`count_traces(logs_dir)`**: the number of `run_end` events in `logs/*.jsonl` (read with `read_trace`; a file that cannot be read is skipped and counted in a `unreadable` number). `0` when the folder is missing. This is the "traced runs" number of architecture 5. The block also shows how many result lines of the given passes have a trace with a `run_end`.

**`render_markdown(passes)`** builds the block, in this order:
1. **Passes:** one row per pass: pass id, model, validation, retry, code (short fingerprint), complete (`30/30` or `incomplete 17/30`), success `n/N (rate) [low–high]`, calc / search / file / multi-tool successes, tool calls, failed (rate), validation errors, tool retries, step retries, replans, crashed, pauses, median seconds.
2. **Pooled groups:** one row per group with its pass ids.
3. **Ablation**, **Model comparison**, **Before vs after fixes**: the rows of `compare_groups`, or `none` for an empty table.
4. **Not compared:** the reasons.
5. **Traced runs:** `count_traces` and the per-pass trace coverage.
6. A fixed note: `30 tasks per pass: one task = 3.3 percentage points. Intervals are 95% Wilson intervals.`

Rates are printed with one decimal (`63.3%`). The block holds no current time or anything else that changes between two runs on the same files, so running it twice gives the same text.

**`write_block(doc_path, block)`**:
- File missing: create it with `# Results`, an empty line, and the two markers around the block.
- File has exactly one start marker followed later by exactly one end marker: replace only what is between them. Everything outside stays byte for byte.
- Anything else (no marker, one marker, two start markers, end before start): `ReportError`, file unchanged.

### 5.4 `evaluation/analyze.py`: what went wrong in a pass
`analyze_pass(data, logs_dir)` reads each result line and its trace (`trace_path(run_id, logs_dir)`). A missing or unreadable trace is listed in `missing_traces`, and only the trace-based numbers skip that run.

**Outcome class** (`classify`), first rule that matches:
1. `success`: `success is True`.
2. `infra`: `is_infra_error(error)` (a task recorded after 3 pauses, D40).
3. `crash`: `error` is not empty.
4. `wrong_answer`: `status == "done"` and a check failed.
5. `planner_failed`: `status == "failed"` and the trace has no `plan_created` event (unknown without a trace: falls to rule 6 or 7).
6. `gave_up_right_answer`: `status == "failed"` and `checks_passed is True`.
7. `gave_up`: `status == "failed"`.
8. `other`: anything else (for example an unknown status).

**Failed tool calls**: every `tool_call` event with `ok` false, grouped by `(tool, error_kind(error))`, with a count and the first run id. `error_kind`: the text before the first `:` (or the whole text), lower-cased, digits replaced by `#`, whitespace collapsed, cut to 60 chars. Examples: `"file not found: notes2.txt"` → `file not found`; `"transient: timed out after 3 s"` → `transient`; `"no such file 12"` → `no such file ##`. Sorted by count, highest first.

**Repeated failing calls** (first-run problem P4): inside one run, a `tool_call` with `ok` false whose `tool` and `args` (compared as JSON with sorted keys) equal an earlier failed call of the same run. `runs` = runs with at least one repeat; `repeats` = number of such calls.

**Rejected attempts without a tool call** (first-run problem P2, smoke-2 file-02): a `critic_verdict` with a verdict other than `approve` with no `tool_call` event since the previous `critic_verdict`, `plan_created` or `replan` event of the same run. Counted in total and by category. **Why:** this is the mechanical trace of "the critic demanded a tool on a step that needed none". It does not prove that cause; it shows where to read.

**Iteration-limit hits** (D18): `critic_verdict` events whose `output` starts with `Step not completed: tool iteration limit reached.`

**Tool not used** (known weak spot, D39), information only: `search` without `web_search` in `tools_used`; `calc` without `calculator`; `file` with neither `read_file` nor `write_file`; `multi-tool` with fewer than 2 different tools. This never changes success (the checkers decide that).

**Plan steps and step retries** per category, from the result counters (`plan_steps`, `step_retries`).

**Digests**: one per result that is not `success`, in task order: task id, outcome class, run id, check details, the plan steps of the last `plan_created`/`replan`, every critic feedback with its step and verdict, at most 10 failed tool calls (`tool`, short args, error), and the final answer. Text from results and traces is untrusted (web text, model output): each field is redacted with `_redact`, collapsed to one line, backticks replaced by `'`, and cut (final answer 300 chars, feedback 200, args and error 150 each). **Why:** the digest goes into a committed Markdown file; it must not hold local paths or break the Markdown.

`render_analysis` prints the counts as small tables, then the digests. `--out` writes the same text to a file (parent folders created).

### 5.5 The passes (run by Gaurav)
Pass ids: `<main|second>-<off|on>-<n>`. `main` = `gpt-oss:120b-cloud`, `second` = `gemma4:31b-cloud`; `n` = 1 before the fixes, 2 after. The manifest's `model` is the truth; the report always shows the model, not the alias.

`.env` for every pass: the defaults of architecture 3 with `MAX_REPLANS=1` (D36). Only `OLLAMA_MODEL` and the two flags change between passes. `off` = `ENABLE_VALIDATION=false` and `ENABLE_RETRY=false`; `on` = both `true`. Claude never reads `.env` (Hard rule 7); it checks the manifests instead, which hold the same config keys as `run_end.config`.

Order, most important first, so a usage cap hurts the least:
1. `main-off-1`, `main-on-1`, `second-on-1` (baseline, current `main` code). These can start right away: building `evaluation/` does not change the fingerprint.
2. Analyse the baseline (`python -m evaluation.analyze`), name the top 3 causes (section 5.6), fix, `/test`, `/code-review`.
3. `main-on-2`, `main-off-2`, `second-on-2` (after the fixes **and** after the code-review fixes, so the measured code is the code that is merged).
4. `second-off-2` if quota allows; `main-on-3` (a repeat, for run-to-run variance) if quota still allows.

After each complete pass: commit `benchmark/results/<pass_id>/` (D37) with `chore(results): pass <pass_id>`. If a pass pauses, resume it later with the same command and the same `.env`. Do not delete `logs/` during this session: the traces are local only and are needed for the analysis and the trace count.

### 5.6 Choosing and making the fixes
1. Run `analyze` on `main-on-1` and `main-off-1` (and `second-on-1`), save to `docs/analysis/<pass_id>.md`.
2. Gaurav and Claude read the counts and digests and name **up to 3 causes**, each with its count (how many failed tasks or wasted retries it explains) and run ids as evidence. They go into `docs/results.md` under "Failure analysis (before fixes)". Candidates already known: P2 (planner splits trivial steps; critic demands a tool on a step that needs none), P4 (the same failing call repeated), P6 (citation markers in answers), and the D39 weak spots. The traces decide; a candidate with no evidence is not fixed.
3. **Spec addendum:** section 10 "Chosen fixes" is added to this spec (one subsection per fix: cause, evidence, change, its acceptance criteria), committed as `docs: update spec for evaluation`, and Gaurav approves it before any fix is written. **Why:** the fixes cannot be known before the traces exist, but they still go through the spec → approval step.
4. Each fix is one commit (`fix(<area>): ...`) changing only `src/` and `tests/`, with at least one regression test for that cause, and one decision entry (D-number) with the cause, the evidence and the expected effect.
5. After the post-fix passes, the "Before vs after fixes" rows show whether each fix helped. A fix that did not help is reported as such.

### 5.7 `docs/results.md`
Hand-written sections around the generated block:
- **Setup:** models, dates, the shared config, pass ids, the commits measured.
- **Headline numbers:** taken from the block (post-fix passes; open question 2), written next to the targets, with the intervals.
- **Failure analysis (before fixes):** the top 3 causes, counts, evidence run ids, links to `docs/analysis/`.
- **Fixes:** what changed, decision numbers, and the before/after rows.
- **Limitations:** 30 tasks (one task = 3.3 points), a cloud model is not fully repeatable at temperature 0, the model knows most search facts without searching, outcome classes and the "rejected without a tool" count are code heuristics, and anything else the traces show.

## 6. Acceptance criteria

**Passes and metrics** (`tests/evaluation/test_passes.py`, pass folders in `tmp_path`)
- [ ] AC1: `load_pass` returns the manifest, the result lines and the number of pause lines; `complete` is `True` only when the result count equals the manifest's task count. It raises `ReportError` for an invalid id (`"../x"`, `"Main"`), a missing pass folder, a broken manifest, and a broken results line (the message names the line number).
- [ ] AC2: `pass_metrics` on 4 scripted results gives the same `success_rate`, `by_category`, `failed_tool_call_rate` and `crashed` as the runner's `summarize`, plus the summed `validation_errors`, `tool_retries`, `step_retries`, `replans`, `runs_with_failed_call`, and the median duration in seconds; `fingerprint_short` is 8 hex characters.
- [ ] AC3: `wilson_interval(15, 30)` is within 0.001 of `(0.3315, 0.6685)`; `wilson_interval(0, 30)[0] == 0`; `wilson_interval(30, 30)[1] == 1`; `wilson_interval(0, 0) is None`.
- [ ] AC4: Two complete passes with the same model, config, fingerprint and task ids form one group whose counts are the sums and whose rates are recomputed from the sums (scripted so that the mean of the two rates differs from the pooled rate); an incomplete pass is in no group; passes that differ only in fingerprint are in two groups.

**Report** (`tests/evaluation/test_report.py`)
- [ ] AC5: An off group (both flags `false`) and an on group (both `true`) with the same model, fingerprint and other config give one `ablation` row; off 10 failed of 100 and on 8 of 100 give a relative reduction of 0.2; off 0 failed gives `None` (`n/a`); on 12 of 100 against off 8 of 100 gives a negative reduction, printed as an increase.
- [ ] AC6: No `ablation` row when the two groups differ in fingerprint, in model, in another config key (`max_replans`), or when only one flag differs; each such pair gives a "not compared" reason naming what differs.
- [ ] AC7: Two groups that differ only in `ollama_model` give one `model` row; two that differ only in fingerprint give one `fix` row with "before" being the group with the earlier `started_at`.
- [ ] AC8: `count_traces` on a folder with two traces that end in `run_end`, one without `run_end`, and one non-`.jsonl` file returns 2; a missing folder returns 0.
- [ ] AC9: `render_markdown` gives the same text twice for the same files; it shows rates with one decimal (`63.3%`), every success rate with its interval, `incomplete 17/30` for an incomplete pass, and the fixed 3.3-points note.
- [ ] AC10: `write_block` creates a missing file with the heading and both markers; on a file with both markers it replaces only the text between them (the text before and after is byte for byte the same); it raises `ReportError` and leaves the file unchanged for a file with no marker, only one marker, two start markers, or the end marker before the start marker.
- [ ] AC11: `main(["--passes", "a,b"])` returns 0 and prints the block; returns 2 for an invalid or missing pass and for a `--write` file without the markers; `benchmark.runner.run_task` and `src.config.get_llm` are never called (patched to raise in the test).

**Analysis** (`tests/evaluation/test_analyze.py`, scripted traces in `tmp_path`)
- [ ] AC12: `classify` returns each of the 8 classes for a scripted result built for it, and the rules apply in the order of section 5.4 (a result with `success=True` and a non-empty `error` is `success`; a `failed` run without `plan_created` but with `checks_passed=True` is `planner_failed`).
- [ ] AC13: `error_kind` gives `file not found` for `"file not found: notes2.txt"`, `transient` for `"transient: timed out after 3 s"`, `no such file ##` for `"no such file 12"`, and at most 60 chars for a long error without `:`; failed calls are grouped by tool and kind with counts, highest first.
- [ ] AC14: A run with `read_file {"path": "a"}` failing 3 times and `read_file {"path": "b"}` failing once gives `repeated_failing_calls == {"runs": 1, "repeats": 2}`; the same args with a different key order count as equal; a failed call followed by the same call succeeding is not a repeat.
- [ ] AC15: A trace `plan_created → critic_verdict(retry) → tool_call → critic_verdict(approve) → critic_verdict(retry)` gives `rejected_without_tool.total == 2` (the first and the last verdict), counted under the result's category.
- [ ] AC16: `iteration_limit_hits` counts only `critic_verdict` outputs that start with `Step not completed: tool iteration limit reached.`
- [ ] AC17: `tool_not_used` lists a search task without `web_search`, a calc task without `calculator`, a file task with neither file tool, and a multi-tool task with one tool; it lists none of them when the expected tools are present.
- [ ] AC18: A result whose trace file is missing is listed in `missing_traces`, still gets an outcome class and a digest, and `main` returns 0.
- [ ] AC19: There is one digest per non-success result, in task order. Digest text has no newline and no backtick, has the project folder replaced by `<project>`, and keeps the caps: final answer 300 chars, feedback 200, args and error 150, at most 10 failed calls.
- [ ] AC20: `main(["--pass", "p1", "--out", <path>])` writes the same Markdown it prints and returns 0; it returns 2 for an invalid or missing pass.

- [ ] AC22: Comment tags in `evaluation/*.py` are only the five allowed ones (the same check as session 6 for `benchmark/`).
- [ ] AC23: `code_fingerprint` of a project copy in `tmp_path` does not change when a file under `evaluation/` changes.

- [ ] AC24: `pytest -q` passes with no network and no LLM calls; the existing tests pass unchanged (this includes the session 6 test that fixes the content of `benchmark/tasks.json`).

## 7. Edge cases and errors
- **Usage cap during a pass:** the runner pauses (session 6). Resume later with the same command and the same `.env`. The report shows an incomplete pass as `incomplete n/30` and leaves it out of every group and comparison.
- **`.env` changed by mistake between `main-off-1` and `main-on-1`** (for example `MAX_REPLANS`): the runner allows it (they are different passes), but the report gives no ablation row and names `config.max_replans` under "not compared". Fix `.env` and run the pass again with a new id.
- **Code changed between the two baseline passes** (an edit in `src/` or `benchmark/`): different fingerprints, no ablation row, a "not compared" line. Do not edit `src/` or `benchmark/` while the baseline passes run; `evaluation/`, `docs/` and `tests/` are safe.
- **A task recorded after 3 pauses** (D40): counts as a failed task in the success rate (that is the session 6 rule), shows as `infra` in the analysis, and the limitations section says how many.
- **The off pass has fewer failed calls than the on pass:** possible, because a validation error counts as a failed call, and in the off pass the tool's own input checks (D8) also fail the call. The negative reduction is reported as it is (AC5). It is not a reason to change the metric: the definition is fixed in architecture 5.
- **Both ablation passes have 0 failed calls:** the reduction is `n/a`; the CV must not claim a reduction.
- **The model differs from run to run at temperature 0:** visible only with repeats (`main-on-3`); the limitations section says the numbers are from one or two passes.
- **A trace is missing** (deleted `logs/`, or a run from another machine): the analysis lists it and continues; the trace count is lower; AC31 fails and is reported, not hidden.
- **A broken line in a committed `results.jsonl`:** `load_pass` refuses with the line number, like the runner.
- **Untrusted text in digests** (web text, model output, injected instructions): redacted, collapsed to one line, backticks replaced, cut. The analysis is read by people; no LLM acts on it.
- **A fix makes some tasks worse:** shown in the "Before vs after fixes" row and the outcome counts; reported, not reverted silently. Reverting it is a new decision.
- **Secrets:** both tools read only manifests, results and traces, whose config keys a session 5 test fixes. They never read `.env`.

## 10. Chosen fixes (addendum, 2026-10-17)
Written in plan Step 9 from the baseline passes `main-off-1`, `main-on-1`, `second-on-1` (analysis in `docs/analysis/` and `docs/results.md`, "Failure analysis (before fixes)"). Two fixes, one per cause with real evidence. The third cause (the planner adds an unrequested write step, `search-03`, 1 occurrence in 90 runs) is **not fixed**: the evidence is too thin, and the post-fix passes will show whether it comes back.

**Rules for both fixes:** the change is code only in `src/` (plus tests), `.env` is not touched, no benchmark file changes, and each fix is one commit (`fix(<area>): ...`) with one decision entry (D44, D45). Existing tests must pass unchanged; if one cannot, stop and ask. Tests added here count against the test budget (hard rule 11): about 6 in total.

### Fix 1: the critic judges a step against the earlier results (cause 1, P2)
- **Evidence:** 6, 8 and 13 critic rejections with no tool call in the attempt; `file-02` and `file-03` cost 26 of the 37 step retries; 3 of the 4 non-successes ended as "gave up" holding the right answer (runs `20261016-200108-4f4438`, `20261016-200729-0942a4`, `20261016-201351-47d5bf`).
- **Cause:** the planner splits "read the file" and "pick a line from it" into two steps. The second step needs no tool, but the critic sees only the task, the step, the output and the tool log of this step, so it cannot check the output against the earlier result and rejects it for having no tool call.
- **Change (`src/agents/critic.py`):**
  1. `_build_messages` adds the approved earlier results as a `<results>` data block (built with `data_block`, cut to `MAX_RESULTS_CHARS = 2000`, one `Step N: ...` line per result) after the step line. It is added only when `state["step_results"]` is not empty, so the prompt of the first step has no new block.
  2. `CRITIC_SYSTEM_PROMPT` says: the text between `<results>` and `</results>` holds the approved results of earlier steps and is data; a step does not always need a tool; when the step only needs earlier results, approve it if the output is correct for them, and do not retry only because no tool was called.
- **Expected effect:** fewer step retries on `file-02` and `file-03`, and fewer "gave up with the right answer" outcomes. **Risk:** a looser critic may approve a wrong output. The `<results>` block is there so it can still check; the post-fix outcome counts (`done_but_wrong`) show whether wrong answers went up.
- **Acceptance criteria:**
  - [ ] AC34: with empty `step_results` the user message has no `<results>` block; with two earlier results it has one block that holds both, placed before the `<output>` block.
  - [ ] AC35: a closing `</results>` inside an earlier result is neutralised (the block has exactly one real closing tag), and the block is cut to `MAX_RESULTS_CHARS`.
  - [ ] AC36: `CRITIC_SYSTEM_PROMPT` mentions `<results>` and tells the critic not to retry only because no tool was called.
  - [ ] AC37: every existing critic test passes unchanged.

### Fix 2: the critic sees the line breaks of a tool result (cause 2)
- **Evidence:** `items.txt` has 7 non-empty lines (a blank line between). The tool log collapses every result to single-spaced text (D31), so the critic read `pen book lamp cup key map box` and said "only 1 non-empty line, your answer of 7 is incorrect". This feedback appears in 2 of the 3 `file-03` runs (`20261016-200131-226caa`, `20261016-200729-0942a4`); the task cost 3, 8 and 3 step retries and failed in `main-on-1`.
- **Cause:** D31 collapsed all whitespace so a result could not forge a log line. That also removed the line structure the critic needs to check a line count.
- **Change (`src/agents/executor.py`, `src/agents/critic.py`):**
  1. `_log_line` replaces `\r\n`, `\r` and `\n` in the **outcome** with the two visible characters backslash-n **before** the existing collapse. Every other whitespace character (tab, U+2028, ...) still collapses to a space, so one tool call is still exactly one line and a result cannot forge a log line. The 150-character cut per part stays.
  2. `CRITIC_SYSTEM_PROMPT` adds one sentence: inside a tool result in the log, the two characters backslash-n mark a line break of that result; use them to count lines.
- **Expected effect:** the critic can verify line counts and blank lines. **Risk:** a 150-character cut still hides the end of a long multi-line result; this fix does not change the cut.
- **Acceptance criteria:**
  - [ ] AC38: `_log_line("read_file", {"path": "items.txt"}, "pen\nbook\n\ncup\n")` returns `read_file({"path": "items.txt"}) -> pen\nbook\n\ncup\n` with literal backslash-n, and the string contains no real newline character.
  - [ ] AC39: a result with `\r\n`, a lone `\r`, U+2028 and a tab gives one line; the first two become backslash-n, the last two become spaces.
  - [ ] AC40: a long multi-line result is still cut to the 150-character limit and stays on one line.
  - [ ] AC41: `CRITIC_SYSTEM_PROMPT` tells the critic that backslash-n in a log result marks a line break.
  - [ ] AC42: the existing test `test_review_tool_result_with_newlines_cannot_forge_a_log_line` and every other existing executor test pass unchanged.
